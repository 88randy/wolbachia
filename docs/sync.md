# Field sync API (`POST /api/v1/field/sync/`)

Issue #5. The phone records events offline (decision 2) and uploads them in **sync batches**. One request uploads the batch and pulls what changed for the phone. Code: `backend/field_sync/` (pipeline, registry, `record.void`) and `backend/reviews/` (review items). Contract conventions: [`api-conventions.md`](api-conventions.md). Terms: [`glossary.md`](glossary.md).

## Request

`POST /api/v1/field/sync/` with `Authorization: Bearer <access>` only (a web session cookie is `401`). Permission `field_event.sync` (courier). The organization is the one the token is pinned to.

```json
{
  "device_id": "uuid",
  "sent_at": "2026-11-03T15:00:00Z",
  "cursor": "opaque, optional",
  "events": [
    {
      "id": "uuid generated by the phone",
      "type": "ovitrap.check",
      "schema_version": 1,
      "device_time": "2026-11-03T14:41:10Z",
      "payload": {},
      "shift_id": "uuid | null",
      "gps": { "lat": 19.43, "lng": -99.13, "accuracy_m": 8.5 },
      "rules_version": "hash of the rules snapshot the phone used",
      "catalog_version": "hash of the catalog snapshot the phone used",
      "manual_capture": false,
      "voids_event_id": "uuid | null (only for record.void)"
    }
  ]
}
```

- `sent_at` is the **phone's clock at send time**. The server compares it with its own clock to measure skew.
- `events` may be empty: that is a pure pull.
- `payload` is a JSON object, at most 32 levels deep, without `\u0000` characters, lone surrogates or non-finite numbers (`1e400`). Its content belongs to the event type's handler.
- `sent_at` must fall between 2020-01-01 and 2100-01-01 (UTC), else `400 validation_error` on `sent_at` (`out_of_range`). An event's `device_time` outside the same range rejects only that event (`invalid_payload`, `device_time: out_of_range`). Version tokens and the cursor cannot contain lone surrogates.
- The envelope is validated as a whole (`400 validation_error`, `fields` like `events.3.type`): a batch with a malformed envelope is refused and nothing in it is stored. The phone parks the identified events as local error when a fields key names events.N or events.N.field, releasing the rest because none were ingested. If no valid event index is provided, the whole batch is parked. A sent_at error pauses sending until the clock is fixed.

## Response `200`

```json
{
  "server_time": "2026-11-03T15:00:02Z",
  "results": [{ "id": "uuid", "status": "accepted | rejected | in_review", "code": "accepted", "params": {} }],
  "changes": {
    "cursor": "opaque",
    "reviews": [
      { "id": "uuid", "event_id": "uuid", "kind": "rejected | in_review", "code": "...", "params": {}, "created_at": "..." }
    ],
    "catalog_version": "hash",
    "rules_version": "hash",
    "has_more": false
  }
}
```

- `results` has one entry per event, **in request order**. `code` is `accepted` for accepted events. The phone shows plain-language text from `packages/i18n` (keys `sync.result.<camelCase code>`); the API never returns user-facing text.
- `changes.reviews` are the courier's own review items (rejected or in-review events) after `cursor`. Send the returned `cursor` in the next request. `has_more: true` means "pull again now" (a long backlog is paged, `API_CURSOR_PAGE_SIZE`, default 100). **Deviation from the issue contract:** `has_more` was added; without it the phone cannot tell a full page from the end.
- `changes.catalog_version` and `changes.rules_version` are the `version` hashes of `/field/catalog/` and `/field/rules/`. When one differs from the phone's, it downloads that snapshot (`If-None-Match`).
- The nine domain arrays and root `changes.capture_context` are specified in [bootstrap and projection recovery](#bootstrap-and-projection-recovery-b-13-110) and [paired current capture context](#paired-current-capture-context-289); they do not change event verdicts.
- The phone validates the 200 shape before applying it. A malformed response retries with backoff; missing per-event results become transient failures, while valid results and cursor bookkeeping commit atomically.
- A **final upload** (below) answers with `X-Session-Revoked: true` and an empty `changes` (`cursor`, versions `null`).

## Batch errors (error envelope)

| Status | `code` | When |
|---|---|---|
| `400` | `validation_error` | Invalid envelope, `device_id`, `sent_at`, UUID, etc. (`fields` says where). `fields.sent_at` with code `out_of_range`: the phone's date and time are wrong. **For the app (#6):** ask the courier to fix the device date and time; nothing is lost, the events stay in the outbox and are sent after the fix |
| `400` | `invalid_cursor` | The cursor was not issued by this server for this organization and user, or was edited |
| `400` | `parse_error` | Body is not JSON (or is nested beyond what the parser can follow) |
| `401` | `not_authenticated`, `invalid_token`, `token_expired`, `session_revoked` | No bearer token, bad or old token, revoked session outside the final upload |
| `403` | `device_mismatch` | `device_id` is not the device of the session |
| `403` | `permission_denied`, `no_active_membership` | Missing `field_event.sync`; `X-Organization` names another organization |
| `413` | `payload_too_large` | `Content-Length` over `SYNC_MAX_BODY_BYTES` (checked before the body is read), more than `SYNC_MAX_EVENTS` events, or Django's own body limit |
| `429` | `throttled` | Rate limit per device, with `Retry-After` |
| `429` | `sync_in_progress` | Another batch of the same courier is running; nothing waited. `Retry-After` says when to retry (`SYNC_RETRY_AFTER_SECONDS`) |

A failed request leaves nothing behind (and gives a final upload back).

### What the phone does after a batch error

| Error | Recovery |
|---|---|
| `invalid_cursor` | Drop the cursor and send the request again without it. The server returns the whole backlog from the start; the phone deduplicates review items by `id`. Events in that request were not ingested, so resend them too. |
| `payload_too_large` | Split the batch (fewer events per request) and send the parts one after the other. |
| `sync_in_progress` or `throttled` | Wait `Retry-After` seconds and send the same batch again (event ids make the retry safe). |
| `device_mismatch`, `session_revoked`, `invalid_token` | Not retryable with the same session: sign in again. |

## Guarantees

- **Idempotent.** The event `id` is the primary key. The same id again (also concurrently, also twice in one batch) returns the stored result and creates nothing. Each event runs in its own savepoint: the `INSERT` is the arbiter of a race, and the loser's domain writes roll back with its savepoint. The same id with other content returns the stored result and logs a warning (`payload_sha256` differs). Two couriers (or organizations) that share an id are arbitrated by the primary key and the savepoint, like any duplicate; there are no per-id locks (decision 72). The whole batch transaction runs with `SET LOCAL lock_timeout` (`SYNC_LOCK_TIMEOUT_MS`): an insert that waits too long for another batch's uncommitted row with the same id (`lock_not_available`), or a deadlock between two such batches that share ids in opposite order (`deadlock_detected`), rolls the batch back and answers `429 sync_in_progress`. The phone retries the same batch, which is safe because of the event ids; on the retry each shared id resolves to one `accepted` and one `event_id_conflict`. An id stored by another organization, device or user is `event_id_conflict`.
- **One batch per courier at a time.** Batches of one (organization, user) are serialized with a PostgreSQL advisory transaction lock that is *tried*, never waited for: a second batch (for example from another phone of the same courier) is answered `429 sync_in_progress` with `Retry-After` at once, so a burst of retries cannot exhaust workers or connections (decision 71). The pull of `changes` runs inside the same locked transaction. Inside a batch, events are processed in `(device_time, id)` order (a void sent before its original in the array still works). An event older than the last accepted one is still processed: offline is normal.
- **Partial batches.** An invalid event never blocks the others: its domain writes roll back and, while its device has rejection quota available, the rejected `FieldEvent` is stored with its `ReviewItem`. With no slot left, only that event returns `rejection_quota_exceeded` and remains on the phone (see Rejection quota). Its payload is stored as received, except (decision 74) when it is too large, too deep or not storable (lone surrogate, non-finite number): then a marker `{"_not_stored": "<code>", "size_bytes": n}` is stored instead, so a hostile phone cannot fill the table with junk; a NUL character is replaced by U+FFFD.
- **Precedence** when several statuses apply: `rejected` over `in_review` over `accepted`. Among in-review reasons: `final_upload_after_revoke`, then a handler's own, then the shift's (`captured_after_shift_close`), then `clock_skew`.
- **Clock skew** (decision 62). `skew = sent_at - server_received_at`. If `|skew|` is over `clock_skew_review_seconds` (the value in force when the server received the batch, `rules.selectors.get_values_in_force`), every event of the batch is `in_review` with `clock_skew`; so is an event with `device_time > sent_at + threshold`. Never rejected for skew alone, and an old event sent late is not flagged for being old. With no value configured **[PENDING client]** nothing is flagged, `clock_skew_seconds` is stored on every event and a warning is logged.
- **Doubtful events do not change records** (decision 73). When an event will land `in_review` anyway (`ctx.review_code` is set: final upload or clock skew), a `record.void` is validated but does **not** void its target: the void event is stored `in_review` and the target stays intact until a supervisor accepts it (#113 applies supported original effects once). All handler families use the same no-effect cutover; original plain observations survive separately from their rolled-back writes.
- **Final upload.** A revoked session may upload once when an administrator revoked it with `allow_final_upload` (#4). The events are stored `in_review` with `final_upload_after_revoke`, the answer carries `X-Session-Revoked: true`, the second attempt is `401 session_revoked`. The request holds the user and session locks for its whole duration, so the batch is bounded and nothing in the pipeline or a handler calls an external service.
- **Immutable.** `FieldEvent` and `ReviewItem` are insert-only (model, manager and a PostgreSQL trigger). Only the void fields of an event can change, once.
- **Isolation.** Every row carries `organization_id`. The organization comes from the token, never from the body. A void of another organization's event looks like a missing one.

## Rejection quota (#56, SA09)

`RejectionQuotaCounter` is mutable bookkeeping with `organization_id`, `device_id`, `local_date`
and `count`, unique on `(device, local_date)`. It does not change `FieldEvent` or `ReviewItem`:
those audit rows remain insert-only. The quota counts only **new stored rejected events**.
A revoked phone's **final upload** is never refused by the quota (it happens once and cannot be retried, so its rejections are stored without claiming a slot; it is bounded by `SYNC_MAX_EVENTS`).
Accepted and `in_review` events never claim a slot and are always processed, including when
other events of the same batch hit the quota. Existing review items, pulls and cursors are unchanged.

**Deliberate deviation from issue #56's proposed blanket `429`:** a valid batch still responds
`200` with a result for every event, in request order. Each rejection beyond the quota produces:

```json
{"id": "uuid", "status": "rejected", "code": "rejection_quota_exceeded", "params": {"retry_after_seconds": 43200}}
```

No `FieldEvent` and no `ReviewItem` are inserted for that result. When at least one result has
that code, the `200` response also has `Retry-After: N`, equal to its `retry_after_seconds`.
Without a blocked result the quota adds no header, even if the last available slot was used.

**Phone recovery:** unlike final rejection codes, `rejection_quota_exceeded` means **not stored**.
Never discard that event or its evidence. Keep the original id and payload in the outbox or
quarantine, resend after `Retry-After`, and continue sending valid events. It is a retry control
code, separate from the final, translated rejection verdicts in `REJECTED_CODES`. Mobile handling
and localized copy are outside this backend change. No rejection is fabricated in the review queue
for an event that was not stored; the phone remains the source of that evidence.

The counter day is the batch's `server_received_at` converted with `ZoneInfo(Organization.timezone)`;
never the phone's clock or the deployment's timezone. Every event of a batch uses that one day,
even if processing crosses midnight. The next receipt-local midnight selects a new row; old counters
are retained. The delay is the ceiling of actual seconds to that midnight (UTC instants, so DST
changes are handled), minimum 1. UTC midnight does not reset a Mexico City counter.

The Nth rejection is stored; the (N+1)th is not. A stored rejection replays its original result
without claiming a slot, including at full quota. A blocked event has no server row, so retrying it
on the next local day validates and stores it normally. Different devices have independent quotas;
two couriers sharing a device share its quota. Quotas start counting new rejections at deployment;
there is no audit-row backfill or deletion. Operators must use the same deployment limits on all workers.

### Atomic claims and lock order

The race rule is a unique device/day row plus a conditional database increment, never a Python
read-then-write check. Inside `EventProcessor._reject`'s own savepoint, `get_or_create` (unique index
arbitrates concurrent creation) is followed by `UPDATE ... SET count = count + 1 WHERE count < limit`.
The row stays locked until batch commit. The event and review item are inserted after the claim.
A duplicate event id rolls back that savepoint, including the claim and any scheduled alerts, then
replays the stored result. If a claim fails after waiting for the final slot, the processor rechecks
the stored id: a concurrent winner must resolve as a replay or `event_id_conflict`, rather than quota.

Order: any final-upload `User` / `DeviceSession` locks first; courier advisory try-lock; handler row
locks of the event; quota counter in the rejection savepoint. Nothing after the counter explicitly
locks a user, device, session or token row. Rejected handler writes/locks are rolled back before
rejection storage; locks from earlier successful events may remain until batch end. A later event
may run its own handler, so domain-row cycles remain subject to the existing bounded wait policy.
Each batch has exactly one authenticated device and one receipt-local day, hence at most one quota
row: two batches cannot acquire *different quota rows* in opposite order. Shared devices serialize
slot claims on that row even for different couriers. See [`accounts/README.md`](../backend/accounts/README.md#row-lock-order).

The counter's creation/update and deferred FK checks run under the existing `SET LOCAL lock_timeout`.
SQLSTATE `55P03` or `40P01` follows the existing `sync_batch` mapping to `429 sync_in_progress`;
it rolls back the **whole batch**, counter increments, events, review items, alerts and any final-upload
consumption. This 429 retains its short `SYNC_RETRY_AFTER_SECONDS` delay, distinct from the quota's
per-event `200` response and local-midnight delay.

### Operator alerts

Logger `field_sync.services` emits a warning only when a successful claim equals
`ceil(limit * percent / 100)` for a configured threshold. Default: once at 80% and once at 100%,
never for a replay or an unstored rejection. A duplicate percentage is normalized once at settings
load. Several distinct percentages may round to one count; each still emits its own crossing.
Structured fields and the log line carry only `organization`, `device`, `local_date`, `count`,
`limit`, `threshold_percent`, without personal data or payloads. `transaction.on_commit` discards
alerts from a rolled-back savepoint or batch; a successful retry alerts once. This is operator logging,
not notification delivery (#49), and does not aggregate or change review items (#22).

Implementation APIs: [Django atomic get-or-create/update](https://docs.djangoproject.com/en/5.2/ref/models/querysets/),
[on-commit and savepoints](https://docs.djangoproject.com/en/5.2/topics/db/transactions/#savepoints),
[drf-spectacular response headers](https://drf-spectacular.readthedocs.io/en/latest/drf_spectacular.html#drf_spectacular.utils.OpenApiParameter).

## The `changes.cursor`

A signed token (`django.core.signing`) bound to the organization and the user and valid for `SYNC_CURSOR_MAX_AGE_SECONDS`: a forged, edited, copied or expired cursor is `400 invalid_cursor` (recovery above). It holds the `courier_sequence` of the last item delivered: a counter per (organization, courier), assigned `max + 1` when the review item is created, never a timestamp. A clock that goes back, or two items created in the same instant, cannot make the phone skip an item. That is gap-free because the sequence is assigned, and the pull runs, under the courier's batch lock. The phone still deduplicates by `id` (a retry after `invalid_cursor` returns items again).

> **Rule for every writer of a courier's review items (#22 and any later epic):** take `field_sync.services.lock_courier_batches` for that (organization, courier) first and create the item only through `reviews.services.create_review_item`, which assigns `courier_sequence`. A writer outside the lock could commit a lower sequence behind a cursor already issued. The unique constraint `(organization, courier, courier_sequence)` only catches a writer that forgot the lock; it does not replace it.

## The handler registry (`field_sync/registry.py`)

Each epic owns its event types. It registers one handler per `(event_type, schema_version)` from its `AppConfig.ready()`:

```python
from field_sync.registry import EventHandler, register


def ready(self) -> None:
    register(EventHandler("ovitrap.check", 1, OvitrapCheckPayload, apply_ovitrap_check))
```

| Piece | Contract |
|---|---|
| `payload_serializer` | A DRF serializer for `payload`. It gets `context["request"].organization`, so `OrgScopedPrimaryKeyRelatedField` works. Failure is `invalid_payload`. |
| `apply(ctx, data)` | Writes the domain records. Return normally for `accepted`; raise `EventRejected(code, params)` to roll **every** write back and store the event `rejected`; raise `EventNeedsReview(code, params)` to roll back operational writes/callbacks and retain the immutable source `in_review`. |
| `ctx` | `organization`, `user`, `device`, `envelope` (the validated event), `server_received_at`, `review_code` (set when the event will be reviewed anyway; its operational writes will roll back) and `rules_at(at)` (lazy: the rule values in force at `at`, usually `device_time`). |
| `on_void(ctx, voided_event)` | Optional. Runs in the savepoint of a `record.void` that voids an event of this type; may raise `EventRejected` to refuse. |

Rules for handlers: keep row locks short: the batch runs under `SET LOCAL lock_timeout` (`SYNC_LOCK_TIMEOUT_MS`, 3 s), which also bounds the `select_for_update` waits of handlers, and a longer wait turns the **whole batch** into `429 sync_in_progress` (it rolls back and the phone retries); validate your own unique constraints and raise `EventRejected`, never let the database detect them (an `IntegrityError` from a handler is a `500` for the whole batch, because it cannot be told from a corrupted state); declare every code you raise in `EventHandler.codes`; write only through the current transaction and only domain tables (no code outside the savepoint, or a rejection would leave debris); no external calls (HTTP, storage, email: the view may hold locks); no user-facing text; never trust `organization_id` from the payload. Registering a pair twice raises `ImproperlyConfigured`. `tests/test_sync_registry.py` checks the contract of every registered handler (shape, and that each declared `codes` entry has its `sync.result.*` key in both locales and a row in this document), so a new epic gets that check for free.

### Append-only reviews (#113)

A NEW `in_review` source has no operational effects. The pipeline retains its
preparation locks, rolls back a separate inner operational savepoint (including
its operational callbacks), then stores the immutable FieldEvent, ReviewItem,
source observations, causal identity and original evidence links. Critical-review
audit publication is recoverable after commit; outboxed never means delivered.

`causal_parent_pending` retains an owned typed parent dependency without dispatching
work or inventing a parent row/FK. A missing declared void target is preserved in
the original envelope independently of its nullable relational FK. Later valid
resolution appends a fact and never fills that old FK or retargets the source.
Exact source replay still returns its original result. Accepting a parent does
not automatically replay its children.

`motorcycle_safety_hold` retains a capture for review while an actual or derived
motorcycle safety hold blocks work. A pending severe review is not a fabricated
MotorcycleBlockEvent. Accepting a severe source can create its real fault once;
it cannot authorize departure or clear that fault. Closure-only work on an owned
legacy frame preserves safety holds and does not accept its opening.

Supervisor decisions append separately from ingest status. A valid acceptance
applies the original registered operation once or adopts a complete proven legacy
materialization; it writes a unique effect receipt in the same transaction.
Unknown history, unavailable handlers, changed fuel comparison context and
mandatory safety/evidence gaps remain explicit blockers. A new audit photo cannot
replace the original declared mandatory upload UUID. Source timestamps, payload
hash, rule/catalog references and original ReviewItem sequence never change.

The single typed `history` producer publishes actual review/whole-shift decisions
through CourierChange and a publication receipt. Current real source/whole-shift
subjects are authorized before LIMIT, cursor and bootstrap, including every
applicable center/quadrant pair. Captured subject vectors remain audit data and
never become durable permission. Unknown-context audit is nonterminal/pending
and is not broadcast without a safely proven subject vector.

### Shifts (#68)

**Motorcycle authorization (#201).** `shift.open` requires the current paired
`field_event.sync` grant for the motorcycle's center; `motorcycle.read` and
`motorcycle.manage` are not required and never widen that grant. An unassigned
motorcycle (`center = null`) requires an explicit all-center sync grant. Quadrant
scope is inapplicable and cannot substitute for center scope. Unknown, foreign,
voided and out-of-scope motorcycles all return `motorcycle_unknown` with empty
params before blocked/in-use state is examined. A non-locking lookup and current
scope check reject an unavailable motorcycle before waiting for its row lock, so
contention on an out-of-scope motorcycle cannot turn that answer into a revealing
`429 sync_in_progress`. An authorized candidate is then row-locked and its current
center and grants are rechecked. Each scope check captures active membership and
profiles in one SQL statement through the shared selectors, without a configuration
row lock. The locked recheck is the final authorization snapshot, including on a
final upload; a downloaded bundle or the event's capture time never supplies
authority. Scope changes committed before that snapshot apply to pending events.

A shift is the courier's day. The phone generates the shift UUID and sends it as the envelope `shift_id` of `shift.open`; every later event of that day carries the same `shift_id`. `GET /shifts/` and `GET /shifts/{id}/` (permission `shift.read`: supervisor, admin) read the result; see `api-conventions.md`.

**`shift.open`** (schema 1): `shift_id` required; payload `{motorcycle_code: str, odometer_km: int, checks: [{item: str, result: "ok"|"minor"|"severe", note?: str}], note?: str}`. `item` is the `code` of an active item of the closed catalog `motorcycle-check-item`, at most once each; the list may be empty (the checklist is configured per organization, so the server does not require every item). Rejections in this order: `invalid_payload` (shape, unknown or repeated checklist item, missing or reused `shift_id`), `motorcycle_unknown`, `odometer_out_of_range`, `shift_already_open`, `motorcycle_blocked`, `motorcycle_in_use`. The field codes inside `invalid_payload` `params.fields` are: `checks: ["unknown_item"]` (an item that is not an active item of `motorcycle-check-item`), `checks: ["duplicate_item"]` (the same item twice), `shift_id: ["required"]` (missing) and `shift_id: ["already_used"]` (the id belongs to a shift already, also one inserted by a concurrent batch of another courier, also of another organization: one answer for all). When a `severe` line and a decreased odometer coincide, `severe_check` wins and the decrease is not reported separately. A `severe` line retains the source `in_review` (`severe_check`) without creating a Shift/check/block; it derives a pending safety hold until a valid acceptance or explicit safety disposition. An open below the highest odometer (open or close reading of any shift) ever recorded for the motorcycle in the organization retains the source `in_review` (`odometer_decreased`) without opening a Shift. The reference is the maximum because an odometer only goes up: it needs no ordering of shifts (events of one batch share their receipt time and the phone's clock cannot be trusted).

**`shift.close`** (schema 1): `shift_id` required; payload `{odometer_km: int, note?: str}`. `shift_not_open` when the shift does not exist, is another courier's or another organization's (the same answer) or is already closed. An odometer below the open reading retains the source `in_review` (`odometer_decreased`) without closing the Shift; the immutable captured values are not lost. The threshold is "any decrease" [ASSUMPTION; a rule parameter if the client wants a tolerance].

**Events that name a shift.** Every other event with a `shift_id` (except `record.void`, which may correct an event of any day) is checked first: a shift that does not exist, is another courier's or another organization's is `rejected` `shift_not_open`; a closed shift accepts events whose `device_time` is not after `closed_at_device` (offline work often reaches the server after the close) and stores later ones `in_review` `captured_after_shift_close` (no operational effects, `ctx.review_code` set). `shift_not_open` is only ever a rejection. The check is a registered envelope check (`field_sync.registry.register_envelope_check`, registered by `shifts` in `AppConfig.ready()`); with none registered the pipeline validates nothing. Handlers that must not run outside a shift (`location.ping`, #8) also require `shift_id`, which the pipeline cannot know.

**Ordering.** Inside one batch events are processed by `(device_time, id)`, so an open and its close work in any array order. Across batches the phone sends its outbox in order. A close/child with a proven owned pending typed parent is retained `in_review` with `causal_parent_pending`; unknown/foreign/ambiguous parents keep the existing safe denial. No parent row/FK or automatic child replay is invented. Two events with the same `device_time` are ordered by id, which is arbitrary: the app must not stamp an open and its close with the same instant.

**One open shift per courier and per motorcycle** are enforced by partial unique indexes (`shift_one_open_per_courier`, `shift_one_open_per_motorcycle`); the handler checks first (the motorcycle row is locked, so two couriers cannot both pass) and a reused shift id that loses a race on the primary key is caught in its own savepoint and answered `invalid_payload`, so none of them is an `IntegrityError` for the batch. Batches of one courier are already serialized (try lock), so two phones of the same courier opening together give one `accepted` and one `429 sync_in_progress` (or, when they run one after the other, `shift_already_open`). `Shift` and `MotorcycleCheck` also have database triggers: no deletes, a checklist line is never updated, a shift is only updated by closing it while open. A shift event cannot be voided by its author (`shift_event_not_voidable`): corrections are a supervisor's (#34).

## Bootstrap and projection recovery (B-13, #110)

`GET /api/v1/field/bootstrap/` requires a live pinned device bearer token and
`field.bootstrap`. Session cookies cannot authorize it. The organization comes
from the authenticated membership/token, never URL/body. The once-only default
permission seed adds the grant to existing seeded courier/admin profiles:
`manage.py seed_organization_defaults --apply`; subsequent reruns preserve an
administrator's later revocation. Admin includes it for explicit delegation.

Response fields are `bundle_version`, `schema_version`, `generated_at`,
`scope_revision`, `cursor`, `catalog_version`, `rules_version`, `next_change_at`,
`map_manifest_ready`, `capture_context` (#289), followed by these fixed sections in order: `assignments`,
`supplies`, `permits`, `eligibility`, `history`, `map_manifests`, `quadrants`,
`sampling_points`, `ovitraps`. Every section is
present as a list, even when its dependency has no producer. Catalog/rules versions,
due time, schema and map readiness are deliberate additions to the issue contract.
`schema_version` is an opaque SHA-256 of the bundle contract version and registered

`cursor` and `generated_at`; timestamps/signature renewals alone do not change it.

unsent evidence. After an invalid cursor, fetch bootstrap WITHOUT If-None-Match (a fresh cursor
requires a 200 body), replace projections, then
resend the same pending event ids with the new cursor. Ingest deduplicates them.
[ASSUMPTION] Native atomic store integration is M-01; this backend exposes and
tests the recovery contract, not actual phone storage.

A revoked phone still has only its explicitly authorized one final sync upload:
it gets empty reviews and all nine typed arrays, null cursor/configuration versions

## Cursor v2 and compatibility

The signed payload is `{o, u, s, c, r}`: organization, courier, last delivered
review sequence, last delivered CourierChange sequence, and scope revision hash.
The revision hashes canonical EFFECTIVE membership/profile intersections with
only the relevant permission codes (`field.bootstrap`, `field_event.sync`),
keeping each action grant paired with both center and applicable quadrant scopes.
None/empty denies; all must be explicit. Grants from different profiles never
cross-combine. Scope is computed, not stored on the courier.

The hash also binds the monotonic `revision` of the membership and of each active assigned
profile, and `bundle_schema_version` (#196): restoring identical grants after a revocation, or
registering a new producer, invalidates every older cursor, because rows published while a courier
was outside the scope, or before a producer existed, have no CourierChange for that courier. The
phone recovers with `invalid_cursor` -> bootstrap. Unrelated profile edits cause one extra
bootstrap (accepted cost; correctness over bandwidth).

Missing c/r (v1), malformed, expired, foreign-owner or scope-mismatched tokens
return 400 invalid_cursor before any events in that request are ingested.
[ASSUMPTION] No production phone holds v1. Rollout requires regenerating clients
and supporting invalid_cursor -> bootstrap -> retry before deploying cursor v2.
Existing stored events/review items are unchanged; the new feed starts empty.
No token means an initial pull from both sequences zero. Bootstrap sets s=0 for
review-id replay/deduplication and c=max at its locked snapshot boundary.

Sync preserves its existing fields/result order and adds nine typed arrays under
`changes`, each entry `{sequence, action, resource_type, resource_id,
resource_version, data}`. Action is upsert or remove; remove data is empty.
It also adds nullable `changes.next_change_at`. field_event.sync gates upload and
review pull; field.bootstrap governs downloadable domain projections in BOTH the
snapshot and typed feed. A sync-only profile receives no typed projection rows.
This shared projection scope is essential: c=max from bootstrap must never skip
rows exposed only by a different action grant in sync. Both feeds independently page at
API_CURSOR_PAGE_SIZE, advancing s/c only to the last delivered row in that feed.
has_more is true if either feed has another visible row. Replaying an older cursor
may repeat entries: clients deduplicate by resource/version and review id.

## Paired current capture context (#289)

The optional, nullable root `capture_context` belongs to bootstrap and changes,
not a new BundleProducer or event envelope. Every current bootstrap 200 and normal
sync page emits an object; every field inside it is required:

| --- | --- |

Each WorkScope has centers and quadrants with explicit mode none/selected/all and

### Consumer recovery and compatibility

The new DTO is additive/optional so old consumers retain their known fields and
opaque-schema handling. The intentional root boundary requires their existing
invalid_cursor→bootstrap recovery. A new consumer with an old/missing/unsupported
normal context must remain capture-unavailable. This does not certify every
historical draft APK or database lineage.

#138 owns strict decoding and local publication: only a validated full bootstrap
can atomically commit context, actual downloaded foundations, owner/session binding
and durable readiness through the existing DayStore writer. A delta or a context
alone cannot clear absent/legacy readiness. A later page can refresh only a matching
already hydrated revision, using equality rather than ordering hashes. Pending
readiness omits If-None-Match and survives offline, write failure, unexpected 304 and
restart; an ordinary 304 retains only its already proven same-owner cache. Known
empty grants deny capture without forcing endless bootstrap recovery.

On invalid_cursor/observed revoke, invalidate current authority before awaiting
recovery, retaining drafts, original rule/catalog/authority facts and outbox/evidence
UUIDs. Missing/null normal metadata where an observation is expected also makes
old context audit-only. A same-session internal no-pull null supplies no new
observation and cannot undo an invalidation. Final mode always blocks new capture;
null does not renew permission. Keep event receipts before existing full cleanup
and #222 retry. Projection publication remains separate from outbox settlement,
with idempotent replay rather than network/file I/O inside one giant transaction.

The local authority revision/CAS advances across absent/null and observed A→B→A
or regrant. It is independent of the server hash. A new login/session/device/issuer/
org or reinstall cannot reuse readiness or adopt old data from a username, same UUID,
matching grant hash or fresh Me alone. No immediate remote erasure is promised for
offline retained bytes; hide active cached access when revocation is observed.

For M09, join an actual physical/fixed point UUID to its real quadrant and center,
then require one complete matching grant at the capture/correction transaction
boundary under the applicable current/original policy. Downloaded rows/tasks,
retained GPS/Assignment, B17 history, B33 receipts and #287 advisory are not current
capture authority. Do not fabricate M08 bags/reuse/stock or rewrite captured events.
The backend addition implements none of those mobile/native integration gates.

## Bundle producer registry and EVERY change writer

Owning apps register `BundleProducer(key, schema_version, build, serializer)` via
`field_sync.producers.register()` in AppConfig.ready(). Allowed keys are exactly
the nine fixed sections; duplicate or unknown keys raise ImproperlyConfigured.
`build(ctx)` returns a deterministic list of dictionaries, using ctx.organization,
ctx.user, ctx.scope (paired EffectiveScope), ctx.now and ctx.permission. It MUST
filter by organization, courier assignment and both applicable scope dimensions.
Every raw row also carries `organization_id`, `center_id`, `quadrant_id` metadata
(null dimension only when genuinely inapplicable). The infrastructure checks
ownership/scope again BEFORE serializer projection. Metadata need not be exposed
by the producer serializer. Missing ownership metadata fails closed. The serializer
validates each emitted payload; invalid producer output is a configuration error.
Future dependency PRs must publish concrete section schemas and bump producer
schema_version whenever they change them. Current absent-domain sections are
open object arrays in OpenAPI; no invented domain payload/handler is claimed.

Map producers use MapManifestSerializer (or a subclass), with
`{asset_id, version, sha256, size_bytes, quadrant_id, licensed}`. They must include every required assigned asset, including failures; omitting one
while returning other complete assets would falsely imply readiness. Report
failed/unavailable assets with incomplete metadata (empty sha256/version or zero
size) or an empty section. Missing/incomplete/unlicensed assets keep
map_manifest_ready=false. True means server metadata is complete, not that the
phone has downloaded and verified it; native readiness also requires local
licensed asset/hash verification. No network/storage/tile downloads run here.

EVERY CourierChange writer must use this sequence, in one database transaction:

1. Honor existing User -> Device -> DeviceSession -> TokenPair lock ordering.
2. Hold the actor's `lock_courier_batches(batch)` for sync. Geography web writers
   serialize Organization first and use `fanout_courier_changes` to take every
   affected courier lock before writing. See the shared fan-out rule below.
3. Write the domain projection and call append_courier_change(batch, ChangeInput(...))
   before committing; kind must have a registered producer. The service validates
   schema/scope/action and allocates max+1 for the organization/courier.
4. Keep the lock through commit. Never allocate outside it, publish later from an
   on_commit callback, use timestamp watermarks, or perform network/storage/mail
   under the lock. Scope loss invalidates the cursor; voids are upsert tombstones,
   never UPDATE/DELETE or remove. Future remove writers must send empty data.

A transaction-local connection marker guards append and rolls back with savepoints;
it cannot authorize a later transaction. CourierChange uses OrgScopedModel and
ImmutableMixin, a positive unique organization/courier/sequence constraint and
PostgreSQL insert-only trigger. Bootstrap reads max, builds every section and
issues its cursor in ONE transaction under that same try-lock. Bootstrap and sync
capture membership, user/organization activity and active assigned profiles from
ONE SQL statement: an ArraySubquery of same-organization profile snapshots is part
of the membership SELECT. Under READ COMMITTED, a transaction alone cannot prevent
a separate profile SELECT from observing a newer configuration than the membership.
The shared effective_scope algebra consumes these captured profiles without another
query, preserving government restrictions and paired grants. No Organization row
lock is taken here: configuration writers lock Organization before their targets,
and taking that lock after the courier lock would add a reverse lock-order edge.
See [Django ArraySubquery](https://docs.djangoproject.com/en/5.2/ref/contrib/postgres/expressions/)
and [PostgreSQL READ COMMITTED](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED).
Sync captures one effective context under the courier lock, validates scope,
ingests and pulls with that SAME context/revision inside the transaction. It must
not recompute r after ingest: a concurrent configuration commit must leave the
issued old revision detectable on the next pull, requiring bootstrap to remove
revoked projections. Thus no compliant writer can commit
a sequence behind an already-issued cursor. Try-lock/lock-timeout contention maps
to retryable 429 sync_in_progress with Retry-After; the request has no partial effect.

### Tombstones and immutable scope (D4, D7b)

Voiding placement or reading emits an ovitrap upsert and retains the identity in
bootstrap. `placement_voided` says whether the placement itself is voided.
`voided` indicates a retained correction marker; `voided_resource_type` identifies
placement/reading, and `voided_event_id` identifies the SOURCE FieldEvent that was
voided (distinct from reading_id, an OvitrapReading UUID). void_reason_code and
voided_at are explicit; no author's identity or free-text reason is downloaded.
The latest correction marker stays in bootstrap even after a replacement check.
A reading tombstone carries the recomputed latest unvoided state, or nulls when
none remains. placement_voided=false means such a reading correction does not
void the whole ovitrap. Existing readings still block placement void (#111). Voiding a reviewed event
with no operational placement/reading preserves OvitrapVoid history and emits no
projection: there is no downloaded row to correct.

SamplingPoint.block and Block.quadrant are immutable: a point never transfers
between quadrants or centers. Quadrant republish upserts its revision plus each
point changed by keep/move/remove resolutions and its ovitraps. Here move relocates
inside the same block identity; remove retires the point (`is_retired=true`),
without deleting it. Unchanged points produce no redundant changes. Block and
point creation/publication also emit their exact written versions. No move writer
or scope-remove fan-out is added. Loss of an effective grant is handled by the
existing scope revision r -> invalid_cursor -> bootstrap replacement (#110),
which removes inaccessible projections while preserving independent drafts/outbox.

### Shared transactional fan-out (D6)

`field_sync.services.fanout_courier_changes(FanoutScope(...))` is the only fan-out
helper. Domains call it inside their domain write transaction; field_sync imports
no domain producer/writer. All organization writers serialize configuration with
Organization FOR NO KEY UPDATE. The helper captures active memberships, active
user/organization and same-organization active assigned profiles using the same
single-statement scope snapshots as bootstrap. It reuses effective_scope (including
government restrictions) and requires one paired field.bootstrap grant covering
BOTH the current center and quadrant. Sync permission alone never downloads rows.
No live membership means no recipient, even if an old session remains.

[ASSUMPTION] SYNC_MAX_FANOUT_COURIERS defaults to 1000, must be positive and is
configurable by environment. To bound work before scope evaluation it caps active
candidate memberships with an active assigned field.bootstrap profile in the
organization, not only those passing the final center/quadrant intersection.
The query fetches at most cap + 1. Exceeding the cap fails closed with HTTP 503
fanout_limit_exceeded, before domain writes, with no partial feed. Operators must
size the cap for the pilot organization; there is no background delivery fallback.

Account locks retain User -> Device -> DeviceSession -> TokenPair. Sync already
holds the actor's courier advisory lock, then takes Organization and the existing
point/ovitrap/void-target locks. The helper takes remaining recipient try-locks in
ascending `(advisory_key, user_id)` order, skipping transaction-local markers for
ALL already-held locks (including actor, earlier events and savepoint-safe locks).
Geography takes Organization -> all recipient try-locks -> Quadrant -> descendants.
These additional locks NEVER wait; they cannot create a wait cycle across the
different domain entry paths. No later account locks are taken. Any failed try-lock
raises the existing retryable 429 sync_in_progress/Retry-After and rolls back the
whole write; event-savepoint rejection also rolls back every feed append.

Only after ALL recipients are locked does the caller insert domain effects and
append one CourierChange per row/recipient with a per-courier CourierContext.
That context carries organization/user, without fabricating a web device.
The generic void pipeline has already marked its source FieldEvent inside the
same savepoint before invoking on_void; contention rolls that marker back too.
Lock markers survive only their transaction and roll back with savepoints. Locks
remain held through commit. No on_commit delivery, network, Celery or timestamp
watermark is involved. A bootstrap under the same courier lock either includes
the committed row with c >= its change, or receives that change on a subsequent
pull. Replayed event IDs short-circuit the handler and append nothing; subsequent
pulls using the returned cursor do not repeat delivered changes.

Selectors apply organization and both paired dimensions in SQL before reading
rows; raw rows also carry organization_id/center_id/quadrant_id for ctx.includes.
Joined identities and correlated latest-state subqueries keep the three producer
builds to at most four SELECTs regardless of row count (two reference queries,
one point query, one ovitrap query). This bound excludes existing catalog/rules,
permission capture and cursor queries. The regression grows points and readings.
