# Mobile foundations spike (issue #1)

Throwaway proof-of-concept. It exists only to answer the questions in `issues/01-spike-mobile-foundations.md` on real company phones. Nothing here is production code and nothing here is imported by `mobile/`.

Results go in `REPORT.md` (same folder). This file explains how to build the app, install it on a phone from Windows, run each test and record evidence.

## 1. What is in the app

One bottom tab per spike item.

| Tab | Spike item | Main libraries |
|---|---|---|
| Store | Local store: WatermelonDB vs op-sqlite, 10k events, pending queue, survive app kill | `@nozbe/watermelondb`, `@op-engineering/op-sqlite` |
| QR | QR scanning, torch, scan time, camera permission denied | `react-native-vision-camera`, `react-native-vision-camera-barcode-scanner` |
| Map | Offline map pack, size, render time | `@maplibre/maplibre-react-native` |
| Go | "How to get there" with a `geo:` URI, Organic Maps missing | local native module `modules/device-control` |
| Speed | Speed lock overlay above 10 km/h, latency | `expo-location` |
| Admin | Device Owner status, lock task mode, in-app APK update | local native module `modules/device-control` |

Why an Expo project with native folders generated by `prebuild` (and not a plain React Native CLI project):

- The React Native docs recommend a framework for new apps and name Expo (`https://reactnative.dev/docs/environment-setup`).
- `@maplibre/maplibre-react-native` 11.x declares `expo >= 54` as a peer dependency, so a plain React Native project would have to fight the package.
- The app needs custom native code (lock task, PackageInstaller). Expo local modules (`modules/device-control`) are autolinked and written in Kotlin.
- The result is a normal Android project in `android/` that you build with Gradle. There is no Expo Go and no Metro server at test time: the release APK bundles the JavaScript, so offline tests are honest.

Versions are pinned in `package.json` / `package-lock.json` (React Native 0.88.1, Expo SDK 58). Do not upgrade them during the spike.

## 2. Prerequisites (Windows)

1. **JDK 17.** The machine has JDK 8 (and a JDK 15). Both are too old: React Native's docs recommend JDK 17 and warn that newer versions may cause problems (`https://reactnative.dev/docs/set-up-your-environment`), and Gradle 9.x needs Java 17 or newer to run (`https://docs.gradle.org/current/userguide/compatibility.html`). The generated project uses Gradle 9.4.1 (`android/gradle/wrapper/gradle-wrapper.properties`).
   - Install any JDK 17 distribution (for example Microsoft OpenJDK 17 or Temurin 17). IT installs it; the spike scripts do not.
   - Do not remove JDK 8. Point only the build shell at JDK 17:
     ```powershell
     $env:JAVA_HOME = "C:\Program Files\Microsoft\jdk-17..."   # your real path
     $env:Path = "$env:JAVA_HOME\bin;$env:Path"
     java -version      # must print 17.x
     ```
2. **Android SDK pieces** (install with Android Studio, SDK Manager). The generated project asks for the following (read from `node_modules/react-native/gradle/libs.versions.toml`; Expo may override, so trust the error message of the first build if it differs):
   - SDK Platform 37 (`compileSdk`), Build-Tools 37.0.0, NDK 27.1.12297006, CMake (SDK Tools tab).
   - Command-line Tools (latest), so licenses can be accepted: `sdkmanager --licenses`.
   - Currently installed on the reference machine: platform `android-35`, build-tools `35.0.1` and `36.0.0-rc4`, no NDK. That is not enough.
   - `ANDROID_HOME` must point to the SDK (`%LOCALAPPDATA%\Android\Sdk`).
3. **Node 22 and npm** (already installed: Node 22.13, npm 11).
4. **A real Android phone** with Developer options and USB debugging enabled, plus a USB cable that carries data.
5. **adb check:**
   ```powershell
   adb version
   adb devices        # the phone must show as "device", not "unauthorized"
   adb shell getprop ro.build.version.release   # Android version, write it in REPORT.md
   adb shell getprop ro.product.model           # phone model, write it in REPORT.md
   ```

## 3. Build the APK

Run everything from `spikes/mobile-foundations`.

```powershell
npm ci                 # install exact versions from package-lock.json
npm run typecheck      # must print nothing
npm run prebuild       # generates android/ (not committed, it is git-ignored)
cd android
.\gradlew.bat assembleRelease
cd ..
```

Output: `android\app\build\outputs\apk\release\app-release.apk`.

Notes:

- The first Gradle run downloads Gradle itself, Android dependencies and (if licenses are accepted) missing SDK packages. It takes a long time and needs internet.
- The generated `release` build is signed with the template debug keystore (`android/app/debug.keystore`). That is fine for the spike and it is what makes the update test work: v1 and v2 are signed with the same key. Never ship this key.
- Do not run `npx expo ...` before `npm ci` finished: without local node_modules, `npx` can pick an old global `expo-cli`. Use the `npm run` scripts.
- If the build fails, copy the first error into REPORT.md section "Build problems". Typical causes: wrong JDK, missing NDK / platform, licenses not accepted.

## 4. Install on the phone

```powershell
adb install -r android\app\build\outputs\apk\release\app-release.apk
```

If you get `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, run `adb uninstall mx.pyrobyte.spikes.foundations` and install again. (The package id is a placeholder chosen for the spike.)

Open the app "Foundations Spike". It has six tabs at the bottom. Every screen has an on-screen log; film the screen so the log and the physical test are in the same video.

Useful for all tests:

```powershell
adb shell screenrecord /sdcard/spike-NAME.mp4      # max 3 minutes per file, Ctrl+C to stop
adb pull /sdcard/spike-NAME.mp4 .
adb logcat -s DeviceControl:* ReactNativeJS:*      # native and JS logs
```

Store evidence (videos, screenshots, log text) in a shared folder that is **not** this repository, and write the link in REPORT.md.

## 5. Tests, one per tab

Record the phone model and Android version for every row in REPORT.md. Repeat each test on each phone model that is available.

### 5.1 Store tab: WatermelonDB vs op-sqlite

Goal: write 10k events, read the pending queue, survive an app kill, compare the two libraries.

1. Select **op-sqlite**. Press "Clear table". Note "Free storage".
2. Press "1. Write 10000 events (one batch)". Write down the time.
3. Press "2. Write 200 events one by one". Write down mean / p95 / max (this is the realistic case: one event per user action).
4. Press "3. Read pending queue". Write down the three timings.
5. Press "4. Mark first batch as sent", then step 3 again.
6. **Kill test:** with about 10k rows in the table, force-stop the app (Settings, Apps, Foundations Spike, Force stop), open it again, go to the Store tab. The "found on disk at open" log line must show the same count as before. Record it.
7. Select **WatermelonDB** and repeat steps 1 to 6. The log line after opening shows the dispatcher: `asynchronous` or `jsi`. Record it. See limitation below.
8. Reboot case: with pending rows, run `adb reboot` (or power off by hand), unlock, open the app, check the count again.

Limitation, read before comparing: WatermelonDB's fast mode (JSI) on Android needs extra native wiring (a separate `watermelondb-jsi` Gradle project and the NDK) that its Android installation docs describe only as manual steps, and the PoC does not do it. The PoC asks for JSI and falls back to the asynchronous bridge, so the WatermelonDB numbers are the "async bridge" numbers. [ASSUMPTION] JSI mode may not work at all on React Native 0.88, which only supports the New Architecture; the 0.28.0 JSI package is written against the old `ReactContextBaseJavaModule` API. If WatermelonDB numbers look bad, state clearly in REPORT.md that they are not JSI numbers.

### 5.2 QR tab: scanning

1. Press "Request camera permission", allow it.
2. Press "Start camera", then "Arm (start timing)", point at a QR code. The time to first read appears.
3. Test: sunlight (outdoors, real label), shade, damaged label (scratched / folded / partially covered), small and large codes, torch on and off. 10 reads per condition; write the median and the failures.
4. **Permission denied:** deny in the dialog, then check that the screen explains it and "Open app settings" works. Also test "deny and don't ask again" (Settings, Apps, Permissions, Camera, Deny).
5. Library note: in VisionCamera 5 the Android scanner is a separate package, `react-native-vision-camera-barcode-scanner`, built on ML Kit (`com.google.mlkit:barcode-scanning:17.3.0`, the bundled-model variant, so it should not need Google Play services to download a model). [ASSUMPTION] confirm on a phone without Google services if the company has one.

### 5.3 Map tab: offline pack

**Important policy finding.** The OpenStreetMap Foundation tile policy (`https://operations.osmfoundation.org/policies/tiles/`) says offline use is not permitted on `tile.openstreetmap.org`, and that bulk pre-fetching or "pre-seeding" areas is not allowed. So this PoC does **not** point the offline pack at the OSM server. Default source: the MapLibre demo style (`https://demotiles.maplibre.org/style.json`, which MapLibre's own docs say is for development only), at low zoom, so the test is small. To get numbers that matter you need a tile source that allows offline use: your own tile server (for example vector or raster tiles generated from an OSM extract and served from the company's DigitalOcean) or a commercial provider whose terms allow it. Ask the client which one; this is a decision for REPORT.md.

1. Online: open the Map tab. The map renders. "Last full render" shows the time.
2. Optional: enter your own raster tile URL template (`https://your-server/{z}/{x}/{y}.png`) and press "Apply style". The attribution text under the map must match your source (the PoC always draws "© OpenStreetMap contributors"; change `MAP_ATTRIBUTION` in `src/config.ts` if your source needs different text).
3. Edit `src/config.ts` first if you want a real quadrant: `MAP_PACK_BOUNDS` is `[west, south, east, north]`, plus min/max zoom and the tile cap (`MAP_TILE_COUNT_LIMIT`). Rebuild after editing.
4. Press "Download offline pack". Write down: time to "complete", number of tiles, size (shown as "Size (all resources)").
5. **Offline test:** enable airplane mode, force-stop the app, reopen, go to the Map tab, press "Reload map". Film that the pack area renders. Write down the render time offline. Also zoom/pan outside the pack and record what happens.
6. Storage: note the pack size next to "Free storage" (Admin tab).
7. [ASSUMPTION] A `file://` style URL works for creating a pack (used when you enter a tile template). If the pack fails with a style error, host the style JSON on your server and put its https URL in `DEFAULT_MAP_STYLE_URL`.

### 5.4 Go tab: Organic Maps via `geo:`

1. Install Organic Maps (package `app.organicmaps`, F-Droid listing `https://f-droid.org/en/packages/app.organicmaps/`).
2. Press "Check if Organic Maps is installed" (expect true), then "Open in Organic Maps". It must open on the test destination. Press Back and check you return to the spike app. [ASSUMPTION] Organic Maps handles `geo:` links; this test verifies it.
3. Uninstall Organic Maps. Press the buttons again. "Open in Organic Maps" must say it is not installed. "Open with any map app" shows what Android does with no handler (chooser, Google Maps, or an error).
4. Repeat with lock task mode on (see 5.6): Organic Maps must be in the allowlist, which the "Enable lock task" button does for `app.organicmaps`. Try also after removing it from the allowlist to see the failure mode.

### 5.5 Speed tab: speed lock

The threshold is `SPEED_LOCK_THRESHOLD_KMH = 10` in `src/config.ts`. It is a default: in the product the value is a rule parameter from the backend.

1. Press "Start watching GPS" and grant location permission.
2. Walk (under threshold: no overlay), then ride a motorbike or car as a passenger above 10 km/h: the red overlay must appear; slow down: it must disappear. Film the phone screen together with the real speedometer.
3. Record from the log: "fix age" (how old the GPS fix is when the app receives it) and "callback to overlay layout" (time inside the app). Total latency you care about is fix age plus app time; the PoC cannot measure GPS chip latency.
4. **GPS off:** turn Location off in quick settings. The screen shows "Location services on: false" after pressing Start again. Record what the app can and cannot do.
5. **Weak GPS:** stand indoors. Record the accuracy values and whether the overlay flickers.
6. Library note: speed is `location.coords.speed` in m/s (`expo-location` types). It can be `null`; the app treats `null` and negative as "unknown" and does not lock.

### 5.6 Admin tab: dedicated mode and in-app update

All of this needs a phone that is a **Device Owner**. Use a spare phone: provisioning requires a factory reset (or a device without accounts).

#### Provision Device Owner (procedure for internal IT)

Source: Android "Dedicated devices cookbook", section "Development setup" (`https://developer.android.com/work/dpc/dedicated-devices/cookbook`). It says: install the app, check that there are no accounts on the device, then run `adb shell dpm set-device-owner <package>/<admin receiver>`.

1. Factory reset the phone. In the setup wizard: skip adding a Google account and skip any account sign-in. (Accounts block the command.)
2. Enable Developer options and USB debugging. Connect the phone; `adb devices` must show it.
3. Install the APK (section 4).
4. Run:
   ```powershell
   adb shell dpm set-device-owner mx.pyrobyte.spikes.foundations/expo.modules.devicecontrol.SpikeDeviceAdminReceiver
   ```
   Expected: `Success: Device owner set to package ...`.
5. Check: open the Admin tab, press "Refresh status": "Is Device Owner" must be `true`. Or:
   ```powershell
   adb shell dumpsys device_policy | findstr /i "owner"
   ```
6. If it fails, record the exact error text in REPORT.md (IT section). [ASSUMPTION from general knowledge, not from the fetched docs] common causes are accounts on the device, the device already completed setup with a user account, or an OEM restriction (some vendors need an extra "USB debugging (security settings)" switch). Per phone model, the working recipe is part of the deliverable.
7. To start over without a factory reset, press "Release Device Owner (test cleanup)" in the Admin tab. [ASSUMPTION] this uses `DevicePolicyManager.clearDeviceOwnerApp`, which Android documents as for testing; if it is missing or refuses on a phone model, factory reset.

For production, provisioning from a QR code at first boot is the documented method (`https://developer.android.com/work/dpc/dedicated-devices`, "Provision dedicated devices": factory reset, then enroll, QR recommended). The QR payload for this app (APK download URL and checksum) is not built in this spike. [ASSUMPTION] record in REPORT.md whether IT will use adb per device or QR.

#### Lock task mode

1. Press "Enable lock task (allowlist this app and Organic Maps)". The app calls `setLockTaskPackages` then `startLockTask` (Android docs: `https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode`). Expected: Home and Recents are hidden; status bar shows only system info.
2. Verify: try Home, Recents, pull the notification shade, power button long press. Record what the user can still do.
3. Check "Lock task state" = `locked`.
4. **Reboot:** with lock task on, reboot. Record whether the app starts again by itself and whether the phone is locked to it. [ASSUMPTION] without being the home app (`addPersistentPreferredActivity`, cookbook "Be the home app") the app will NOT start by itself after reboot. This spike does not set the home app; record the result and note whether it is needed.
5. Press "Disable lock task..." to leave. If you get stuck in lock task: `adb shell am task lock stop` [ASSUMPTION, from memory, untested] or the Admin tab buttons; as a last resort factory reset.

#### In-app update

Docs: a Device Owner can install and update packages without user interaction through `PackageInstaller` sessions (cookbook, "Install app packages"). Other apps get a confirmation screen.

1. Build v1 as in section 3 and install it (it is `versionCode 1`).
2. Edit `app.json`: set `android.versionCode` to `2` and (optional) `version` to `1.0.1`. Run `npm run prebuild` and rebuild (section 3). Copy the APK to a separate folder and rename it, for example `C:\spike-apk\app-v2.apk`. Do **not** install it with adb.
3. SHA-256 of v2:
   ```powershell
   Get-FileHash C:\spike-apk\app-v2.apk -Algorithm SHA256
   ```
4. Serve the folder from the PC (any web server; this uses Python):
   ```powershell
   cd C:\spike-apk
   python -m http.server 8000
   ```
   The phone and the PC must be on the same network; allow the Windows firewall prompt. Find the PC address with `ipconfig`. The URL is `http://<PC-IP>:8000/app-v2.apk`. (Plain http is allowed in this PoC only because the toggle "Allow plain http" is on and `usesCleartextTraffic` is set for the spike. Production must use https.)
5. On the phone (v1 installed, Device Owner set), Admin tab: paste the URL and the SHA-256. Press "Download". Progress is shown. Press "Install downloaded APK".
6. Record: was there any confirmation screen (expected none on a Device Owner phone), how long until the app restarted, did it restart by itself (the PoC registers a `MY_PACKAGE_REPLACED` receiver that tries to relaunch; Android may block background launches, record the result), does it come back into lock task mode, what version the Admin tab shows afterwards, "Last update time".
7. Repeat on a phone that is **not** Device Owner: the user must confirm. Record it.
8. **Download interrupted:** start the download, switch on airplane mode halfway, wait for the error, switch it off, press "Download" again. The PoC resumes only if the server supports HTTP Range requests; `python -m http.server` does not, so it will restart from zero. Record which one happened and the bytes. Use a server with Range support for a proper resume test (for example nginx, or an object-storage URL).
9. **Corrupt / wrong file:** enter a wrong SHA-256. Expected: "SHA-256 mismatch" and the file is deleted.
10. **Storage almost full:** fill the phone (see 6), try the download: the app should say "Not enough free storage" before downloading (it checks twice the file size, because the file is copied into the install session).
11. Logs: `adb logcat -s DeviceControl:*` shows the install status codes.

#### JS-only OTA (alternative, not built)

Not implemented in this PoC. Research item for REPORT.md: Expo's update protocol can be served from your own server (`https://docs.expo.dev/technical-specs/expo-updates-1/`; the page is aimed at organizations running their own update server). The page ties each update to a `runtime version` that describes the native code it needs, so JS-only OTA cannot replace the APK for native changes. Whether JS-only OTA is worth adding on top of APK updates is a recommendation to write in REPORT.md; no code or test exists yet.

## 6. Edge cases (from the issue)

| Case | How to test |
|---|---|
| Phone reboot with pending queue | Store tab: write rows, `adb reboot`, reopen, check "found on disk at open". |
| Storage almost full | `adb shell "dd if=/dev/zero of=/sdcard/fill.bin bs=1M count=NNNN"` until free storage is a few MB (check "Free storage" in the Store or Admin tab). Then run Store step 1, the map pack download and the APK download. Expected: a readable error, no crash, no half-written data. Clean up: `adb shell rm /sdcard/fill.bin`. [ASSUMPTION] `dd` is available in the phone shell; if not, use a file manager app to copy big files. |
| GPS off / weak accuracy | Speed tab, section 5.5 steps 4 and 5. |
| Camera permission denied | QR tab, section 5.2 step 4. |
| Update download interrupted | Admin tab, section 5.6 "In-app update" step 8. |

## 7. Known limits of the PoC

- The Kotlin module (`modules/device-control`) was written against the Expo Modules API and Android docs but, on the machine where it was written, no Android build could be run (JDK 8 / 15 only, no NDK or platform 37). The first Gradle build is also its first compile. Fix compile errors in place; they are expected to be small.
- WatermelonDB runs without decorators and in async-bridge mode (section 5.1).
- No UI polish, no i18n, no tests.
- The `geo:` link, lock task and install code paths were not exercised on a phone by the author.
