# Relocations (W31, #160)

`/operations/relocations` uses the generated relocation list and B33 decision
actions. URL filters, ordering and pages belong to the shared table controller;
`relocation=<proposal code>` owns the shareable decision sheet. Exact scoped
`?code=` resolution precedes every command. Unknown and inaccessible codes have
the same unavailable state.

`relocation.read` requires explicit nonempty center and quadrant scope. Only
`relocation.decide` reveals command controls; the backend rechecks the actual
grant binding and source. Scope changes cancel and remove obsolete query
contexts. Draft reasons remain in private memory above replaceable reads and
are discarded when the selected source becomes inaccessible. A different user
or organization remounts the whole workspace.

B33 uses expected revision **zero** for an undecided proposal. Both approval and
rejection require a reason. The source point code, original version, coordinates,
capture times, evidence references and evaluated rules remain visible. The UI
never turns captured advisories into independent scientific rules.

One guarded explicit command owns each submission. A conflict refreshes source
evidence without overwriting the reason; a fresh explicit refresh precedes retry.
Reauthentication and stale responses never replay writes or publish a receipt.
Only the actual command response establishes a next-day task or published point
version. The contract has no standalone relocation detail or decision-history
read; reopened decided proposals show source status, without invented receipts.
Evidence IDs do not imply downloadable photo URLs. Coordinate fields provide the
map alternative without adding another map widget.

`relocations.test.tsx` covers rejection/task receipts, conflict refresh and retained
input, read-only controls and unavailable sources. `relocation-command.test.ts`
uses a deferred response to protect the single in-flight command and stale-session
publication boundary. Browser R7 coverage belongs to `web/e2e/w-19.spec.ts`.
